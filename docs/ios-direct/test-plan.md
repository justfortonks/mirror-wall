## G1 — full-display capture / encode / stub send

### Bounded implementation proposal

One ordinary iOS app target; no broadcast extension, microphone, camera, Photos or network receiver for G1. Info.plist: normal bundle/version metadata, `UIBackgroundModes` array containing **only `screen-capture`**, and iOS 27 deployment target in build settings. For the same app's later Radio mode, declare `NSLocalNetworkUsageDescription` explaining offline receiver discovery, and `NSBonjourServices = ["_mwiospoc._tcp"]`; obtain consent in foreground. No audio mode or silent-audio workaround; no persistent-content-capture or Wi-Fi Aware entitlement assumed. Inspect final signed entitlements and embedded.mobileprovision, not just Xcode checkboxes.

**Documented (Apple, read 2026-10-16):** [iOS sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-on-ios) uses shared picker `present()` for full display and `presentForCurrentApplication()` for app-only capture; [background modes](https://developer.apple.com/documentation/xcode/configuring-background-execution-modes) lists `screen-capture`. Device behavior and sufficiency for screen-only encode/send remain unverified.

**Hypothesis (flow):** register SCContentSharingPickerObserver, check availability, configure screen-only picker controls, activate shared picker and call `present()`. On selection receive the system filter; create SCStream/SCStreamConfiguration with `.screen` output on a capture queue, start capture and report errors/cancel/system stop truthfully. Resolve exact imported Swift spellings by compiling against this SDK; do not use Mac-only picker-for-existing-stream overloads. Consume valid complete image samples, preserve PTS/color/rotation, explicitly pace at 30 FPS, fit SDR H.264 within 1280×720 / 720×1280 preserving aspect, round encoder-compatible dimensions. Start 6 Mbit/s per phone (brief's 4–6 range), one-second keyframe interval, no frame reordering. Set VideoToolbox real-time/expected rate/bitrate and creation-time low-latency option; log every OSStatus and query hardware use. Unsupported optional properties must be recorded and reviewed, not silently treated as applied.

Use bounded source queue (at most two waiting frames), drop before encode on overload, and a bounded stub-sink queue (≤1 MiB and ≤100 ms; whichever triggers first). Drain encoded access units to a local count/hash/discard sink, never persist screen payload. IDR/rotation reconfiguration and session generations must ignore stale completion callbacks. Stub-send is deliberate queued downstream work on a separate queue; it is **not socket transmission proof**.

Per-second monotonic log: app foreground/background state; capture callback/valid-frame counts; PTS progress/dimensions; encode submitted/completed/error counts and bytes/keyframes; stub enqueued/drained frames/bytes, latest PTS/hash, outstanding queue bytes/age, drops; process memory/CPU if measurable, thermal/battery/charging state; picker/stream/lifecycle events. Persist without a debugger; retain final summaries across foreground return. A timer/UI counter without capture/encode completion is insufficient.

## G2 — synthetic direct radio / two independent sessions

### Bounded implementation proposal

Separate Mac receiver app and Sender Radio mode; no capture API and no screen data. Publish one `_mwiospoc._tcp` receiver with dynamic port; each phone browses Bonjour and connects using discovered service endpoint, with its own authenticated connection/session ID. Enable `NWParameters.includePeerToPeer = true` on **browser parameters, advertised listener parameters and each outgoing connection's parameters**. Use Network.framework TLS/TCP, noDelay; do not force a BSD interface, raw AWDL/NAN, IP discovery shortcut, or multicast socket. Observe listener errors as well as browser/connection errors. Signed Mac app carries matching local-network/Bonjour declarations; if sandboxed, explicitly validate network client/server entitlements, with isolated app configuration.

**Recommendation (Hypothesis): start with TLS even for synthetic data**, using per-run generated throwaway identities held locally, an out-of-band receiver public-key pin entered/compared on each phone, and approved phone keys (mutual TLS or reviewed equivalent). Verify identity before payload; never trust every self-signed certificate or embed a shared private key. TLS is mandatory before real screen/control data. This bounded test identity setup does not claim production pairing/revocation acceptance. If secure identity setup cannot run, mark it blocked; any separately reviewed plaintext synthetic diagnostic must be labeled plaintext and cannot close authenticated G2.

Deterministic non-screen payload records: session/generation, increasing sequence, payload length/checksum and monotonic send time; max 64 KiB payload, incremental parser, limit message size before allocation, at most two active authorized phones and two pending handshakes with five-second timeout. Pacing and receiver acknowledgements expose delivered bytes/gaps/RTT. Cap outstanding app work per phone at 150,000 bytes and 100 ms at target rate (whichever first); stop/report overload instead of accumulating. Log network-stack send completions separately from receiver-delivered acknowledgements; bound outstanding unacknowledged payload too. Separate control/ping scheduling so throughput cannot hide a hung control path.

Choose **6 Mbit/s per planned video sender** before running. Planned aggregate = 12 Mbit/s; two-times headroom = **24 Mbit/s delivered synthetic payload aggregate**, **12 Mbit/s per phone simultaneously for five minutes** (decimal bits/s, excluding headers/TLS overhead). One-phone qualification also uses 12 Mbit/s for five minutes; it does not replace two-phone result. Changing planned media bitrate requires recalculating and recording headroom before retest.

Diagnostics at start, every path/state change and per-second interval: service discovery/add/remove/endpoints; browser/listener/connection states and exact errors; negotiated TLS version/peer-key fingerprint (no secret); session mapping; NWPath status, available/used interface types via supported APIs, interface index/name where exposed, expensive/constrained flags, IPv4/IPv6/DNS support, local/remote endpoints where API exposes them; path viability/better-path events. Log packet/byte counters, actual sent/received/acknowledged payload, protocol bytes/overhead where measurable, sequence/checksum failures, RTT median/p95, queue bytes/age, memory/CPU and radio/battery/thermal. Interface names and `.wifi` alone are not proof of direct routing.

### Tiny Mac Wi-Fi Aware probe

**Verified (local SDK evidence):** framework exists but WACapabilities is `@available(macOS, unavailable)`; see [feasibility](feasibility.md). **Hypothesis (bounded probe):** future native Mac CapabilityProbe first compiles a minimal supported availability check and reports `API unavailable on this SDK` without invoking unavailable symbols. A separate minimal type-check of `WACapabilities.supportedFeatures` may record the compiler's unavailability diagnostic, with no private API/availability bypass. If a later public SDK makes the API callable, log supportedFeatures and maximumConnectableDevices/maximumPublishableServices. Brief expectation is an empty feature set on unsupported Mac hardware; **an actual empty set is not observed and is not interchangeable with compile-time unavailability**. Stop Candidate B if unavailable/empty; Candidate A continues. No Wi-Fi Aware transport or entitlement request belongs in G2. No probe source is created at G0.

### Human steps — decisive no-AP topology (brief §9.1)

1. Install both apps, approve local-network access while foregrounded, complete throwaway identity setup, then quit/relaunch once. Record initial permissions and profile expiry. 2. Place Mac and A/B 1–3 m apart. Record devices, builds, account relationship, room/interference, charging/battery and thermal state. Export current network/radio settings for restoration; alert anyone affected before changing shared network settings. Do not sign A out or sign B in.
3. Unplug **all USB**, disconnect wired/wireless debugging, Ethernet/USB networking, VPNs and other viable relay routes. Disable Personal Hotspot on both phones and Mac Internet Sharing. Disable cellular **data** on both phones for decisive run.
4. Keep Wi-Fi radios **on** on all three. In Settings, remove infrastructure association and disable auto-join for reachable saved networks (or use a controlled environment without reachable APs). Do not use Control Center disconnect as proof the radio is off/on or association cannot recur. Keep Bluetooth enabled initially. 5. Launch Mac Receiver; record listener readiness/service. Launch A in Radio mode, select discovered receiver, compare/approve pin and phone identity offline, start synthetic load. 6. Stop A; launch B and qualify it similarly. Then start A and B **together**, choose the same receiver, verify two independent session counters. Sustain ≥12 Mbit/s each, ≥24 Mbit/s aggregate, for five measured minutes after warm-up. Compare OS/routing evidence before and after to detect auto-association. 7. While both run, stop/disconnect/reconnect A; B must maintain delivery without an unexplained >1 s stall due to A. Repeat for B. Restore auto-join, association, cellular data, VPN, Bluetooth, sharing and other temporary settings to their recorded initial values; record restoration.

## Ratified later acceptance targets — Verified (brief §9/task input)

G3/G4 must still prove two distinct live screens for ≥30 min, each background ≥10 continuous min; aspect-correct 720p-class SDR H.264, target 30 FPS / ≥27 displayed FPS per phone over five simultaneous changing-content minutes, cadence/drops/p95 interval, no unexplained freeze >1 s; optical median latency ≤200 ms and p95 ≤350 ms with same high-frame-rate camera view, sample count and timing resolution. Raw phone-minus-Mac timestamps are diagnostic only. Headroom target above remains synthetic, not video proof.

Also required: trustworthy first-use pairing and 9/10 connections ≤10 s after approvals; one-phone operations must not pause the other >1 s; link-loss recovery ≤10 s after connectivity returns with fresh config/IDR where capture remains authorized (record required consent otherwise); ≥20 start/stop/reconnect cycles; bounded byte/time queues and ≤20% working-set growth minute 5→30, absolute MB and teardown recovery; CPU/hardware codec/thermal/battery reports without persistent serious/critical thermal state; stop/revoke forwarding ≤1 s and truthful stale-picture handling. Full negative identity/pin/token replay/expiry/downgrade/malformed-input/connection-limit/revocation tests remain mandatory before Accepted. Test sleep/wake, force quit, rotation, lock/protected content, interruptions, Wi-Fi changes, reduced bandwidth/loss/delay, Low Power Mode and competing traffic with expected platform limitations separated from recovery failures. No target is lowered by these bounded G1/G2 plans.
