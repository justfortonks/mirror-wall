## 2. Recommended source model

**Proposal — explicit slot mode, one shared listener.** Offer `AirPlay / Android Cast` (existing automatic takeover, default) and `Direct iPhone` in the slot menu only when the development feature is enabled. Reserve selected Direct slots exclusively: they run neither UxPlay, UDP nor CastServer; other slots behave as today. This avoids introducing a third competitor into Android's existing takeover logic. A slot still owns exactly one `H264Renderer`, recorder, feed and window identity.

Keep `MC/SlotConfig.swift` unchanged: its synthesized Codable data already holds names, models, window/feed/bezel/stage settings (`MC/SlotConfig.swift:7–36`), and the store persists it as `slots` (`MW/SlotStore.swift:613–616`). Add development preferences `iosDirectSlotSources.v1` and `iosDirectDeviceSlots.v1`, separate from that data. A new app-side `SlotSource.swift` defines the effective mode; absent entries resolve to legacy. Keep Direct assignments inert while OFF, so legacy slot JSON and the production allow-list need no migration.

| --- | --- |

| New `MW/IOSDirectSlotRegistry.swift` | MainActor atomically maps **HMAC-verified paired device UUID → existing slot ID**, with reverse uniqueness and a reservation lease `(slotID, deviceID, sessionUUID, slotEpoch)`. No routing by name, install UUID, model, TXT or IP. |

**Proposal — admission transaction:** pairing creates a trusted device but does not allocate a stream. Devices UI assigns it to an explicitly selected, stopped/waiting Direct slot; no silent slot creation or occupied-slot takeover. Admission requires that assigned slot to be running and waiting/disconnected with no lease; stopped, unassigned, removed or busy slots produce an authenticated refusal before `welcome`. Retain the prototype's two-active/two-pending limit for G6 even though the wall supports eight slots (`MW/SlotStore.swift:79`; `Shared/Sources/IOSDirectShared/RadioReceiver.swift:200–204,299–303`). Scaling beyond two Direct phones is out of scope.

**Verified:** the existing `makeVideoSession` factory runs **after** active admission and cannot refuse for slot availability (`Shared/Sources/IOSDirectShared/RadioReceiver.swift:313–328`). **Proposal:** add an optional asynchronous admission callback, invoked after HMAC/version/capacity checks and before committing active state or sending welcome. It asks MainActor to reserve the slot, returns a consumer/lease or busy refusal to the receiver queue, and rechecks run, channel, current key and lease before commit. Keep pending/deadline bounds while waiting; roll back leases on timeout/cancel/Forget. Reject synthetic mode in the app; standalone Radio retains it. Preserve the standalone factory as the default when the callback is absent. Never synchronously wait for main from a media queue, or for a media queue while holding a main-owned reservation lock.

**Proposal — lifecycle:** source change explicitly stops that slot, ends its recording part, cancels/drains the old input, invalidates its epoch and resets its renderer before binding the new source. Do not change a busy slot's assignment in place. Stop/restart/remove closes only its Direct session via a new receiver session-cancel API; disable/quit/Stop All also stops the global listener and burns invitations. Re-enable/restart waits for a new authenticated session and fresh config/IDR; it never initiates phone capture. Disconnect clears the picture immediately, publishes Disconnected/standby, releases the lease and retains assignment/window geometry. Healthy TLS with no new pictures shows “Connected; last video …”; do not infer stop versus a static SCK screen. **Verified:** the current wire has no explicit capture-stop message (`Shared/Sources/IOSDirectShared/RadioProtocol.swift:114–133`). **Proposal:** feed authenticated transport health into a Direct watchdog, rather than the UxPlay silence/restart path (`MW/Slot.swift:619–659`). Set Direct `hasPicture`/live state only after actual decode/presentation output, not submission.

**Proposal — alternatives rejected:**

| Alternative | Why not for G6 |
| --- | --- |
| Direct opportunistically takes any legacy slot like Android | Adds three-way admission/restart races and can withdraw a working AirPlay source unexpectedly. |
| Full source-protocol rewrite of all receivers | Larger regression surface than the two explicit lifecycle branches needed now. |
| Synthetic RTP/loopback UDP or a second prototype decoder/view | Adds framing/queueing or duplicates decoding, and bypasses slot recording/feed/window ownership. |
| Add a required source field to `SlotConfig` | Unnecessary persistence/Windows parity work for an experiment; separate preferences provide clean rollback. |

## 3. Media adapter and renderer contract

**Verified:** `VideoAccessUnit` contains generation, sequence, original sender `ptsNs`, keyframe flag and AVCC bytes (`Shared/Sources/IOSDirectShared/VideoProtocol.swift:99–115`). Config parses SPS/PPS and requires four-byte lengths (`:11–52`). Production `H264Frame` is NAL arrays without prefixes, UInt32 timestamp and codec; H.264 keyframes are determined from an IDR NAL (`MC/H264Depacketizer.swift:7–25`). `H264Renderer.render(_:arrival:)` consumes those compressed units, extracts parameter sets and creates its only VT decoder (`MW/H264Renderer.swift:110–166,188–208`).

**Proposal — new `MW/IOSDirectVideoConsumer.swift: RadioVideoConsumer` plus pure conversion helpers in `MW/IOSDirectMediaAdapter.swift`:**

| Input / event | Mapping and invariant |
| --- | --- |
| `videoConfig` | Use `VideoConfigurationState` and `parameterSets()`; retain SPS/PPS for that authenticated session/generation. Validate SPS-derived dimensions against declared dimensions without creating a second decoder, as the prototype does (`Receiver/VideoSessionRenderer.swift:86–117`). Production caches only one SPS/PPS: initially reject configs containing multiple SPS or PPS rather than silently selecting a possibly wrong pair (`MW/H264Renderer.swift:19–20,122–129`). |
| Complete access unit | Walk every four-byte big-endian length, reject zero/overrun/truncated/trailing bytes, and create one `H264Frame(codec: .h264)` from exactly one frame's NALs. No Annex B parser, RTP, depacketizer or encode step. Preserve the 4 MiB input cap before copying (`Shared/Sources/IOSDirectShared/VideoProtocol.swift:118–134`). Verify wire keyframe flag agrees with IDR presence; prepend cached SPS/PPS to each IDR. Reject conflicting in-band parameter sets until a matching new config is accepted. |
| Timestamp | `ticks = (ptsNs / 1_000_000_000) * 90_000 + ((ptsNs % 1_000_000_000) * 90_000) / 1_000_000_000`; then `UInt32(truncatingIfNeeded: ticks)`. Quotient/remainder avoids `ptsNs * 90_000` overflow, preserves sub-microsecond precision until final rounding, and wraps naturally at 2^32. Keep original `seq/ptsNs` for ACK; never reconstruct ACK PTS from ticks. Arrival is **Mac** monotonic `arrivalNs / 1e9`, not phone time. |
| Config repeat / generation change | Identical config is a no-op. Changed config at the same generation or generation regression is a protocol failure (`Shared/Sources/IOSDirectShared/VideoReceiverPolicy.swift:40–51`). New generation resets the Direct decode epoch, pending ledger, timing and prediction chain even if SPS/PPS bytes match. A new connection has an independent generation namespace. |
| Gap / error / timeout | Complete dropped ACK once, invalidate affected pending work, request IDR at most 4/s, and wait for valid config + actual IDR. Preserve the last image during recoverable gaps; disconnect clears it. An old callback may not display, record, publish, ACK twice or update UI after rebind. |

**Verified — missing API, not a ready-made adapter:** renderer `true` means submitted, not decoded; errors/nil output currently return silently (`MW/H264Renderer.swift:107–108,155–166`). The transport's completion must report actual pixel-buffer output and echo original PTS (`Shared/Sources/IOSDirectShared/RadioVideoConsumer.swift:3–12`; `RadioReceiver.swift:218–238`). The prototype already supplies an eight-frame/300 ms decode limit, output deadline and epoch cancellation (`VideoReceiverPolicy.swift:8–37`; `Receiver/VideoSessionRenderer.swift:133–189,248–265`).

**Proposal — narrow opt-in renderer extension:** retain `render(_:arrival:)` and its legacy path; add Direct frame context/completion to the same decode implementation. Tag each submission with session/slot/config epochs and sequence. A bounded per-Direct-session ledger owns completions; output with `noErr` plus image reports `.decoded`, immediate/asynchronous failures report `.decodeError`, and refusal/reset/timeout reports `.dropped`, exactly once. Reuse `VideoDecodeQueuePolicy`; add an aggregate retained-compressed-byte ceiling of 4 MiB, admitting one up-to-cap IDR alone. Enforce age deadlines by a scheduled worker event even if no new frames arrive. Exceeding a bound discards the prediction chain and requests IDR; never drop an arbitrary compressed reference frame and continue decoding inter frames.

Direct configure/render/recovery/close serialize on one slot input executor, also respecting `streamLock`; VT output posts back to that executor. A callback must validate its epoch **before** presentation, `onPicture` and completion. End/drain pending results before resetting/reusing the renderer. Keep callbacks outside renderer/stream locks to avoid synchronous completion deadlocks. The legacy execution path remains unchanged; no prototype `VideoSessionRenderer` or VTDecompressionSession is instantiated in Mirror Wall.

### One presentation clock

**Verified:** legacy presentation shows each decoded callback immediately or schedules it with `PlayoutClock`; picture numbers prevent older scheduled output replacing newer shown output (`MW/H264Renderer.swift:212–255`). That is not the prototype's bounded “decode all, display newest” queue (`Shared/Sources/IOSDirectShared/VideoReceiverPolicy.swift:81–117`). `PlayoutClock` uses wrapped 90 kHz deltas, reanchors on backward/>2 s discontinuities and adds 100 ms when smoothing is enabled (`MC/PlayoutClock.swift:9–14,35–64`).

**Proposal:** add a Direct-only presentation mode inside `H264Renderer`. Decode every admitted frame; deliver every successful decoded picture to `onPicture`; coalesce only decoded display output. Immediate mode holds one newest picture and schedules a single worker drain, without an extra fixed timer. Smooth mode holds at most eight decoded pictures and displays only the newest due picture per drain; use **production `PlayoutClock` once** for due times, with a 300 ms retained-picture age ceiling. Do not run prototype `VideoPlayoutClock` or a second 100 ms buffer outside the renderer. Sequence/epoch, rather than callback arrival order, selects newest. Default Direct smoothing OFF; a Direct per-slot toggle may enable it. Existing global Smoother Motion continues to control legacy slots, with no change to their semantics (`MW/SlotStore.swift:119–120,328–334`).

Count decode success at VT output and displayed frames only after an actual layer enqueue; one picture fan-out counts once, not once per window. `onShow` currently runs before layer enqueue and cannot itself prove display (`MW/H264Renderer.swift:230–255`). Add a Direct presentation-result hook; report hidden/no-ready-layer drops separately and never call an enqueue count physical scanout. ACK success is independent of supersession or visibility. This preserves sender flow control while keeping recording complete and OBS aligned to selected display frames.

### Rotation

**Verified:** orientation hints are presentation metadata, not config/decode transitions (`Shared/Sources/IOSDirectShared/Orientation.swift:5–47`; `RadioReceiver.swift:347–349`). Standalone code composes raw CGImagePropertyOrientation 1…8 with manual/auto degrees (`Receiver/VideoSessionWindow.swift:54–89`). Run 9's pixels remained panel-oriented, while handoff says no usable capture rotation signal is proven (`results.md:250–251`; `handoff.md:190–207`). Production `phoneTurns` describes counterclockwise Android bezel turns, not a pixel transform (`MW/Slot.swift:259–269`; `MC/PhoneBezel.swift:145–155`).

**Proposal:** preserve manual 0/90/180/270, Auto OFF, capture-hint preference over device hints, hint reset per session, and manual value keyed by verified device UUID. Do not copy prototype ⌘R/⌘0 globally: Mirror Wall already uses recording/window commands (`MW/MirrorWallApp.swift:25–27,314–323`). Put Direct rotation actions in its slot menu.

Use a small Direct-only `MW/IOSDirectPictureTransform.swift` after the one VT decode: compose config orientation plus selected rotation into a pooled CoreImage pixel-buffer transform, once per decoded frame, shared by `onPicture`, `currentImage`, and presentation/`onShow`. This keeps screenshots, recordings, tile, stage, pop-out and Syphon consistent without another decode or stream re-encode. Retain at most one raw last image to re-present static content when manual rotation changes; that refresh must not duplicate recording/ACKs. Publish oriented `videoSize`; keep raw size separately for diagnostics. Translate clockwise degrees into bezel counterclockwise turns explicitly, including config orientation; test asymmetric content and all eight base orientations. End the recording part on a presentation-orientation change, including 180°, before subsequent transformed pictures. This adapter's cost/correctness is unmeasured and must pass G6 output/latency checks; auto-rotation accuracy remains a prerequisite, not a solved fact.

## 6. Feature flag and OFF contract

**Proposal — two gates:**

1. Build gate: root manifest reads `MIRRORWALL_IOS_DIRECT_DEV == "1"`; only then adds shared/integration targets, dependency and `MIRRORWALL_IOS_DIRECT_DEV` Swift define for MirrorWall/tests. Wrap new app files and every call site in that conditional. Normal manifest graph and legacy renderer path remain as before.
2. Runtime gate in such a build: UserDefaults Bool `iosDirectEnabled`, absent = false. A development-only Settings toggle “Enable Direct iPhone (experimental)” enables it. `effectiveEnabled = buildGate && defaults.bool(forKey: "iosDirectEnabled")`; no DEBUG-only automatic activation. Dev source/assignment keys are read only after this is true.

**Proposal — OFF must execute the current path byte-for-byte at the compatibility boundaries:** same `slots` encoding, defaults, UxPlay arguments/process count, port/service names, Cast v1 bytes, renderer behavior and existing UI. No Direct listener/browser/Keychain/file/log initialization, pairing prompt, source controls, slot reservation or rewritten source preferences. A stale ON preference in a non-development build has no effect. Switching OFF drains Direct sessions, restores affected slots to their effective legacy mode, and preserves inert assignments for a later explicit opt-in; subsequent startup follows today's path. It does not revoke pairings or restart unrelated legacy slots.

**Proposal — build script opt-in:** add `--ios-direct-dev`; default invocation explicitly supplies `MIRRORWALL_IOS_DIRECT_DEV=0` to **both** Swift build/bin-path calls (`scripts/build-app.sh:7–8`) so an inherited environment cannot alter release builds. Opt-in supplies 1 and creates `MirrorWall-Direct-Dev.app` with bundle ID `com.justfortonks.mirrorwall.directdev`, its own defaults and development Bonjour addition. Do not alter release.yml, make-dmg defaults, updater channels or signing policy. Separate dev bundle identity avoids overwriting the installed app/preferences; ordinary artifacts will differ in build date/version as today, so binary reproducibility is not claimed by the behavioral OFF contract. Run baseline and dev apps sequentially: legacy ports and leftover-UxPlay cleanup are shared (`MW/MirrorWallApp.swift:203–204`; `MW/SlotStore.swift:250–255`); mixed-source testing means one app instance.

## Recommended approach — three sentences

**Proposal:** reserve explicitly selected Direct iPhone slots behind build and runtime gates, using one app-wide authenticated listener and verified-device assignment. Adapt AVCC/config into `H264Frame`, extend the existing renderer only for opt-in decode completion/bounded newest presentation, and reuse its recording, screenshot, Syphon and window outputs. Keep shared sources in place, legacy persistence/protocols and default packaging behavior unchanged, and enter G6 only after standalone acceptance and recorded G5 approval.

**Top three risks:**

1. Two-phone offline/30-minute acceptance, optical latency and recent quality/reconnect changes remain unqualified on devices.
2. Renderer ACK/epoch/queue/rotation adapters could regress recovery or output consistency unless their Direct-only branch and mixed-source isolation are demonstrated.
3. Free-team development success does not establish a signed, persistent, distributable iOS sender and macOS receiver for testers.
